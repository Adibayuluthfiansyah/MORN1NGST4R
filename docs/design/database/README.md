# Database design

Status: design proposal for owner review. **Nothing here is implemented.** No PostgreSQL instance was created, no migration was written or run, and no repository or handler exists. This design is the blueprint for the persistence work of M3 and the slices that follow. Decisions made here carry `DB-nn` IDs. Open questions carry `DQ-nn` IDs and are recorded with their status in `../dq-decisions.md`. Approved decisions (`D-nn`) are cited and not changed. **M3 update (2026-11-18):** the M3 slices are implemented in `services/core/migrations` (00001 to 00007, 00013 to 00015). The result, the rulings and the differences from this design are in `.kiro/specs/mvp/plan.md`, section "Milestone M3".

## Summary

The model has 59 tables and 631 columns in 12 domains (identity 8, policy 1, scope 10, assessment 4, authorization 5, execution 3, audit 2, asset 6, evidence 3, finding 8, integration 8, platform 1). It has 15 migrations: 12 table slices, then indexes, triggers and grants. `mvp-scope.md` classifies every table. The model is relational. There is no graph store (P 9). Evidence bytes are outside PostgreSQL (DB-23).

Baseline facts that come from approved decisions: PostgreSQL 18 from user-installed binaries, a per-user cluster over a unix socket in a 0700 directory, peer authentication, no DSN and no database password (D-67). UUIDv7 generated by the application, forward-only migrations, custom PostgreSQL queue with `FOR UPDATE SKIP LOCKED` leases and fencing (D-80, P-44, P-36). Secrets only in the Secret Service (D-52). Seven finding states with the D-75 transition rules. Report status separate from validation status (D-75).

## Design decisions

| ID | Decision | Why | Source |
| --- | --- | --- | --- |
| DB-01 | One PostgreSQL database `morningstar` with one schema `morningstar`. All objects are schema-qualified. No cross-schema tricks. | Smallest structure that supports least-privilege grants. D-67 gives one per-user cluster. | D-67, P-13 |
| DB-02 | Enumerations are `text` columns with named CHECK constraints, not PostgreSQL `ENUM` types. | See the comparison below. A CHECK is replaced in one transactional migration. An enum value cannot be removed and `ALTER TYPE ... ADD VALUE` has transaction limits. Goose is forward only (D-80). | D-80 |
| DB-03 | Names: snake_case, plural tables, singular columns, `_id` for references, `_at` for timestamps, `_hash` or `_sha256` for digests, `_ref` for opaque references to external stores. | Consistency with sqlc generation and with the API field names (camelCase mapping is mechanical). | structure.md 6 |
| DB-04 | Primary keys are `uuid`, UUIDv7 generated by the application, no database default. | P-47 and D-80. UUIDv7 keeps index locality. Not guessable like a bigint sequence. The domain holds a value type only. `audit_events.seq` is the one identity column (DB-15). | D-80, P-47 |
| DB-05 | No `ON DELETE CASCADE` and no `ON UPDATE CASCADE` anywhere. Every foreign key is RESTRICT. Rows of auditable entities are never hard-deleted in the MVP. State is archived or marked. | A cascade could destroy approval, audit or evidence history. Requirement: avoid cascading deletion that destroys audit evidence. | task rule 10, SEC 13 |
| DB-06 | Four database roles: `ms_migrator` (owns objects), `ms_api`, `ms_worker`, `ms_retention`. One OS user maps to all four through `pg_ident.conf` and peer authentication. Grants follow the matrix in `migration-plan.md`. | Least privilege against mistakes and SQL defects. It does not separate two processes of one OS user, which D-78 accepts. | D-67, D-78, P-13 |
| DB-07 | The single-account rule is a database constraint: `UNIQUE ((true)) WHERE status = 'active'` on `users`, plus account creation locks `bootstrap_secrets` and verifies `users` is empty in the same transaction. | D-60 says one local researcher account. The constraint makes a second account impossible even through a bug. Multi-user is a future migration (DQ-11). | D-60, D-68 |
| DB-08 | All times are `timestamptz`. Decisions that depend on time (approval expiry, lease expiry, grant expiry) use the database clock `now()` inside the statement, never an application clock. | Application and database clocks can differ. One authority removes the race (S1.6). | S1.6, D-48 |
| DB-09 | Every program-owned table has `program_id`. A reference between two program-owned tables is a composite foreign key `(program_id, x_id) -> parent (program_id, id)`, which needs `UNIQUE (program_id, id)` on the parent. Assessment-owned references use `(assessment_id, id)` the same way. | Makes a cross-program link impossible at the database, independent of application checks. Required: no schema silently permits cross-program access. | task rule 12 |
| DB-10 | Scope is versioned by immutable snapshots. Each publication inserts a `scope_versions` header and copies the full rule set into `scope_rules` for that version. The only mutable header column is `superseded_at`. Jobs, approvals, validations, policy decisions and assets store the `scope_version_id` they used. | Re-evaluation of history needs the exact rules. A diff-based history would need replay. Copy-forward is simple and rule sets are small. | D-56, D-61 |
| DB-11 | State machines are append-only transition tables with CHECK constraints listing the legal `(from, to)` pairs and the actor kinds allowed. The parent row holds the current state. A deferred constraint trigger checks that the parent state equals the newest transition. A human-only transition has `actor_user_id NOT NULL`. | Illegal and undocumented transitions fail at the database. Makes the history the authority. | D-75, SEC 5 |
| DB-12 | Database state and process-control state are separate. `jobs.state` says what the system recorded. `jobs.control_state` says what the system asked the process to do (`stop_requested`, `stop_confirmed`, `stop_failed`). A transaction can record the request. Only the worker can stop and confirm. | A transaction cannot stop a running process. Modeling both prevents claiming that revocation stopped work when it only recorded intent (30-second objective, D-48). | D-48, task 3.4 |
| DB-13 | Approval consumption protocol: in the claim transaction (1) lock the job with `FOR UPDATE SKIP LOCKED`, (2) evaluate E2 and insert a `policy_decisions` row, (3) run the conditional `UPDATE approvals ... uses_consumed + 1 WHERE status = 'approved' AND expires_at > now() AND revoked_at IS NULL AND uses_consumed < max_uses`, (4) insert `approval_uses (approval_id, job_id)` (unique), (5) set `jobs.approval_use_id`, lease and `claim_epoch`, (6) insert `job_transitions` and the audit event. Zero rows at step 3 means refusal, audited, no use consumed, no attempt counted. A retry claim reuses the existing `approval_uses` row and never inserts a second one. A deferred trigger checks `uses_consumed` equals the row count. | Atomic, concurrent-safe, and retries cannot create uses (D-30, D-55). | D-30, D-49, D-55 |
| DB-14 | Attempts are separate rows. `UNIQUE (job_id) WHERE termination_confirmed_at IS NULL` allows one unconfirmed attempt, so an attempt cannot be inserted until the previous process tree is confirmed gone. A lease-expired attempt becomes `lost` with the confirmation still null until the worker or the reaper confirms termination. The launch bound is enforced by a conditional counter update in the same transaction as the attempt insert. | D-64 choice 12: a retry waits for confirmed termination, and an intrusive operation launches once. | D-49, D-64 |
| DB-15 | Audit ordering uses `(occurred_at, seq)`. `seq` is an identity column assigned at insert. It can have gaps and a later commit can carry a lower number. Pagination uses the pair as a keyset. | Honest about PostgreSQL identity semantics. No claim of commit-order or gapless numbering. | SEC 13 |
| DB-16 | `audit_events` has foreign keys for `program_id`, `assessment_id`, `job_id`, `scope_version_id`, `decision_id`, `approval_id` and `actor_user_id`. The affected entity is a soft reference (`entity_type`, `entity_id`) with no foreign key. | One audit table covers every entity type, and a typed foreign key per entity would add dozens of nullable columns. Because rows are never hard-deleted (DB-05), a soft reference cannot dangle. A nightly orphan check verifies this. | SEC 13 |
| DB-17 | Append-only and immutable tables are enforced three ways: no UPDATE or DELETE grant to the runtime roles, a `BEFORE UPDATE OR DELETE` trigger that raises, and a `BEFORE TRUNCATE` trigger. Only `ms_retention` may delete `audit_events` rows past retention, through its own audited path. No claim of cryptographic tamper-proofing is made. The keyed hash chain (P-33c) is deferred and accepted (D-78). | Prevents mistakes and SQL defects. The migration role and the database owner can still alter rows (architecture section 17). | D-78, P-13 |
| DB-18 | Report status is not stored on `findings`. The view `finding_report_status` derives Not reported, In draft or In final from `report_findings` and `reports.state`. Validation status lives in `findings.status` and its transition history. | D-75 and the task rule: never one field for both. A derived view cannot disagree with the report rows. | D-75, product.md 7 |
| DB-19 | Indexes exist only for a named query pattern. Each index in `constraints-and-indexes.md` states its pattern. Partial indexes are used for claim, lease, revocation and uniqueness queries. | Avoid speculative indexing and write cost on an 8 GB laptop. | tech.md 15 |
| DB-20 | Migrations contain no seed data. Default policy values are written by the application through the policy use case at first start so they are audited. | A migration that inserts policy would bypass the audit and the human-change rule (D-53). | D-53 |
| DB-21 | A foreign key is created in the migration that creates the later of its two tables. Nullable circular references are plain nullable columns set by UPDATE. The migration order is acyclic. | Keeps each migration independently reviewable. | D-80 |
| DB-22 | Migration conventions: forward only, transactional unless `NO TRANSACTION` is stated, no `IF NOT EXISTS` (fail closed on drift), run only by `ms_migrator` while server and worker are stopped, reviewed before release (SEC 12). | Predictable and auditable. | D-80, SEC 12 |
| DB-23 | Evidence bytes, report files and tool output stay in the local evidence store, addressed by ID. PostgreSQL holds only metadata, digests and the opaque `storage_key`. | D-77, P-08, P-37. Large artifacts do not belong in the database. | D-77, P-37 |
| DB-24 | No secret is stored in an ordinary column. Password, recovery code, bootstrap secret, session token and CSRF token are stored only as hashes (class A). Provider keys and tool credentials are stored only as Secret Service references (class X). `ai_providers.endpoint_url` is checked to hold no userinfo. | D-52, SEC 6. | D-52, SEC 6 |
| DB-25 | `jsonb` is allowed only for open-ended, untrusted or typed payloads that are never filtered by core queries: `operations.parameters`, `observations.payload`, `audit_events.detail`, and small result bags. Each has a size CHECK. Anything queried by a core path is a real column. | Prevents a schemaless core model and unbounded rows. | SEC 11 |
| DB-26 | Deletion model: soft state (`status`, `archived_at`, `revoked_at`, `retention_state`), archival at program level, and permanent deletion only as a future audited retention procedure that deletes leaf rows first. See `data-lifecycle.md`. | Required: distinguish soft deletion, archival and permanent deletion. | task 3.8 |
| DB-27 | After a detected restore the application revokes or cancels the authority recorded in the database (approvals, validations, labs, sessions, enablements, queued and running jobs) before accepting any request. The detection and the procedure are DB-28. | A backup older than the last approval use would restore a consumed use as unconsumed and allow a duplicate launch. | D-30, D-55 |
| DB-28 | Restore detection uses a recovery generation kept in an external owner-only marker file outside PostgreSQL and outside the backup set, compared at startup with the single-row `recovery_state` table and with an audit-sequence watermark. Any missing, invalid, older, newer or mismatching half fails closed into `recovery_required`. Reconciliation is crash-safe and increases the generation. A database-only flag is not the detector. See `recovery-generation.md` for the procedure and the threat boundary. | Anything stored only in the database is restored with it, so only a witness outside the database can show that time went backwards. | D-30, D-48, D-55, D-78 |
| DB-29 | No stored state implies authorization. `approvals.status = approved`, `target_validations.status = current`, `jobs.state = queued` and `lab_registrations.status = active` are inputs to the policy engine at E1, E2 and E3. The claim and launch paths evaluate them again, with the scope version, the validation, the approval, the recovery generation and the exact operation hash. No CHECK or trigger replaces that evaluation. | Database constraints and application authorization are both necessary and neither replaces the other (task principle). | D-05, D-28 |

## Enumeration strategy (DB-02)

| | PostgreSQL `ENUM` | `text` plus named CHECK |
| --- | --- | --- |
| Add a value | `ALTER TYPE ... ADD VALUE`, with transaction restrictions on using the new value in the same transaction | Drop and add the CHECK in one transactional migration |
| Remove or rename a value | Not supported without recreating the type and rewriting columns | Same one-migration replacement |
| Legal transitions | Not expressible | Pairs are CHECK constraints on the transition tables |
| Ordering and storage | 4 bytes, ordered by definition | Text, no implied order |
| Tooling (sqlc, generated Go and TypeScript) | Generates a type per enum | Needs a hand-written constant set, kept in step by a test that reads the CHECK |
| Risk for this project | State sets are still evolving (assessment states, approval classes, tool keys). Forward-only migrations make a removed enum value permanent. | Slight risk of a typo, covered by CHECKs and tests |

Choice: `text` plus CHECK. A test in M3 reads each CHECK and compares it with the Go constants (DB-02).

## Reading the design against the product rules

- **Authorization history is preserved.** Approvals, approval events, uses, policy decisions, scope versions, validations and labs are insert-only or immutable-except-one-column, are never cascaded and are never deleted (DB-05, DB-17).
- **Scope and authorization are independently verifiable.** A job, approval, decision, validation or asset names the scope version it used (DB-10).
- **AI is untrusted.** AI output lands in `plan_items` and `findings` with origin `ai`, in `ai_outputs`, and in `validation_records` as recommendations only. No column can store an AI identity as an approver or verifier: `approvals.decided_by` and `finding_verifications.verified_by` reference `users` (DB-24, SEC 5).
- **Evidence integrity is verifiable.** Immutable metadata with a SHA-256, an append-only check history, and a separate mutable projection (DB-23, P-37).
- **Concurrent workers.** Unique constraints, conditional updates, `SKIP LOCKED` and `claim_epoch` fencing (DB-13, DB-14).
- **Traceability.** `audit_events` plus per-entity history tables answer who did what to which target under which scope version and approval (DB-16).
