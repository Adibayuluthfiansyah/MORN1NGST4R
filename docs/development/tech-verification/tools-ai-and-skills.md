### 2.6 PROPOSED default (not decided)

Three MVP integrations, in this order of confidence:

1. **Subfinder v2.17.0** for passive reconnaissance. Run with an explicit `-s` list limited to sources a human enabled for the program (start with keyless `crtsh` and `hackertarget`), `-oJ`, `-duc`, `-silent`, `-proxy` pointing at the policy proxy, `-config`/`-pc` pointing at job-directory files, never `-active` (it performs DNS lookups that do not use the HTTP proxy, inferred from source), never `-up`.
2. **httpx v1.12.0** for HTTP probing. Run with `-json`, `-duc`, `-no-stdin`, `-proxy` to the policy proxy, no `-p`, `-ss`, `-tls-grab`, `-rdb`, `-pd`, `-auth`, `-unsafe`, `-rr`, `-fr` off (redirects are new targets per policy; httpx follows none by default per README flag description). Input via `-u` from the canonical target list only.
3. **Nuclei v3.11.1** as an optional third integration, classified intrusive (needs approval per product rules), with a pinned template store (nuclei-templates v10.5.2 or a reviewed subset) loaded read-only via `-t`, `-duc`, `-ni`, `-dut`, no `-code`, `-headless`, `-ai`, `-uc`, `-lfa`, `-ev`, `-up`, `-ut`, `-auth`, `-pd`; `-j` output; `-lna` as extra defense. If the owner prefers a smaller MVP, ship Subfinder and httpx first and add Nuclei after the policy proxy path is proven.

Nmap, ffuf and ZAP are not MVP. Nmap's license needs review before any adapter. No tool may be given direct network access: each runs inside the sandbox with only a path to the policy proxy.

Trade-off recorded for the owner: httpx and Nuclei have their own resolver options (`-r`), and Subfinder resolves names itself when `-active` is set. The platform rule "the connection must go to an address that passed evaluation" is therefore not met by passing `-proxy` alone. It depends on whether each tool sends the hostname to the proxy (the proxy resolves and evaluates) or resolves the name first and sends an IP address. That behavior is NOT VERIFIED and decides the enforcement design.

- Arguments determine protection: "the level of protection between the sandboxed processes and the host system is entirely determined by the arguments passed to bubblewrap." Also: "bubblewrap is not a complete, ready-made sandbox with a specific security policy." and "Whatever program constructs the command-line arguments for bubblewrap... is responsible for defining its own security model".
- Setuid mode: "Historically, bubblewrap also supported a setuid mode for systems where unprivileged user namespaces were not supported. However, this has been removed." So v0.13.1 requires unprivileged user namespaces. (The Fedora package description still mentions "works as a setuid binary on kernels without user namespaces", which is stale relative to upstream. - No-new-privs: "bubblewrap uses `PR_SET_NO_NEW_PRIVS` to turn off setuid binaries".
- PID namespace: "PID namespaces ([CLONE_NEWPID]): The sandbox will not see any processes outside the sandbox. Additionally, bubblewrap will run a trivial pid1 inside your container to handle the requirements of reaping children in the sandbox." The man page adds: "bwrap is running a minimal pid 1 process in the sandbox that is responsible for reaping zombies. Inferred: a policy-proxy path into the sandbox needs extra plumbing (for example a Unix socket bind-mounted in plus a relay inside, or a veth set up outside). bwrap does not provide this.
- Mounts: "Everything mounted into the sandbox can potentially be used to escalate privileges." Directories "mounted `nodev` by default".
- System security: the maintainers "believe that it does not, even when used in combination with typical software installed on that distribution, allow privilege escalation. It may increase the ability of a logged in user to perform denial of service attacks, however."
- **File descriptor inheritance: the README and `bwrap.xml` at v0.13.1 contain no statement about which inherited file descriptors reach the sandboxed command.** I searched both for "inherit" and "file descriptor" and found only option descriptions for FD-taking options (`--seccomp`, `--args`, `--sync-fd`, `--file`, `--json-status-fd`, and others). The requirement "close every inherited file descriptor the tool is not meant to receive" therefore cannot be satisfied by relying on documented bwrap behavior. NOT VERIFIED from docs; needs a test (see 3.4). Go's `os/exec` closes non-listed descriptors on the launcher side by default in `exec.Cmd` (not verified here, not fetched).

### 7.1 PROPOSED write-once publish approach (not decided)

1. Evidence root: one directory per program or job, owner-only (0700), on a local filesystem. At start, open it once with `os.OpenRoot` (Go 1.24 or later; Go 1.25 for `Link`/`Rename`) and do all later operations through the `Root`, so symlink escapes are rejected by the standard library.
2. Create a temporary file in the same directory with `OpenFile(tmp, O_WRONLY|O_CREATE|O_EXCL, 0600)`; the temporary name is random, so concurrent writers cannot collide.
3. Stream the content through SHA-256 while writing; call `Sync` on the file; set read-only mode.
4. Publish under the final name derived from the digest with a no-replace operation: `Root.Link(tmp, final)` (hard link; fails if `final` exists), then remove `tmp`. Alternative on filesystems with support: `renameat2(RENAME_NOREPLACE)` through `x/sys/unix`. Treat "final exists" as success only if the existing content hash equals the new one; otherwise report an integrity conflict and do not replace.
5. Open the directory and call `Sync` on it so the new entry is durable.
6. Record the SHA-256, size, provenance and path in the database after step 5; verify the hash again when the evidence is read.
7. Never use plain `rename` onto an existing evidence name.

### 8.1 Exact-bytes execution (inferred, not from a source above)

The platform rule "run the exact bytes that were verified" implies: open the binary once, hash the open file descriptor's content, then execute that same descriptor (for example via `/proc/self/fd/N` or a `memfd` copy) instead of re-opening a path. None of the documents above covers this; it is a design requirement and needs its own validation with `bwrap` (which executes a path inside its mount namespace, so the verified file must be bound read-only into the sandbox and checked inside or via a descriptor-based mount).

### 8.2 PROPOSED default (not decided)

User-installed pinned binaries in a root-owned (or owner-only, read-only) tools directory populated by a documented provisioning step, not bundled in the repository or releases. The tools manifest records: tool name, version, source URL, archive SHA-256 (from the release `digest` and the checksums file, cross-checked), extracted binary SHA-256 computed by us, and for nuclei-templates the tag, commit and tarball SHA-256. The worker re-verifies the digest before each launch. The project's own notices file lists MIT notices if any MIT binary is ever redistributed. Nmap is neither bundled nor required. No automatic update or self-update of any tool.
