# MORN1NGST4R MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. The readiness gate below is closed by decision record 0003. M1 (decision record 0005) and M2 are implemented. Starting any later milestone still needs the owner to say go.

**Goal:** Deliver one complete, authorized, end-to-end assessment on a Linux localhost web application, in small milestones that each end in an independently tested deliverable.

**Architecture:** Go modular monolith (`services/core`) with separate `server` and `worker` processes, PostgreSQL 18, a Next.js App Router UI (`apps/web`), local filesystem evidence, and tools run only in a verified sandbox behind a verified egress path. Domain code is standard-library only. Dependency directions are `structure.md` 5.6.

**Tech Stack:** Pins in `.kiro/steering/tech.md` (Go floor, module path, Node 24 and npm are Decided in D-65 and D-66, other pins stay Proposed until a milestone adds the module): Go 1.27.4 with a `go 1.26.0` floor, Gin v1.12.0, pgx v5.13.0, sqlc v1.31.1, goose v3.30.1, oapi-codegen v2.8.2, Next.js 16.4.6, React 19.3.1, TypeScript 5.9.3.

**Spec:** `.kiro/steering/{product,structure,security,architecture,tech}.md`; owner decisions in `docs/decisions/0001-owner-security-decisions-round-2.md`, `0002-foundation-completion-decisions.md` and `0003-foundation-closure-decisions.md`; product requirements in `docs/PRD.md`; semantics in `docs/decisions/pending/S1-security-semantics.md`; threats in `docs/security/threat-model.md`; spike evidence in `docs/security/feasibility/`.

## Global Constraints

- Domain packages import only the Go standard library and permitted domain packages (`structure.md` 5.6). A library enters a package group only when `tech.md` lists it.
- Fail closed. Unknown, ambiguous or unparseable input is denied. Deny always wins (D-57).
- Wildcard inclusion rules are refused through the MVP (D-35, D-73). Wildcard and CIDR exclusions are accepted (D-57). A refused exclusion is never dropped silently (choice 10 of record 0002).
- Defaults: an in-scope rule without a port covers 80 and 443. An exclusion without a port covers all ports (D-36, D-57). Minimum CIDR prefix /24 IPv4 and /48 IPv6 for in-scope rules and lab ranges, not for exclusions (D-38, D-47, choice 1).
- One approval use per (approval, job), consumed atomically at claim. Three execution attempts for approval-bound active jobs. An intrusive operation has exactly one launch (D-30, D-49, D-55).
- Revocation, scope and lab changes terminate affected work within 30 seconds, measured before it is relied on (D-48).
- Intrusive operations stay disabled until authentication and re-authentication are implemented and tested (D-58). Active operations without established numeric limits stay blocked (O-38, D-71). Password entry is required on every intrusive approval by default (D-69).
- No network-touching tool adapter before the egress path passes its regression gate. No tool execution without the sandbox self-test passing (D-31, D-41, D-42).
- Secrets: Secret Service only, fail closed. Never in argv, environment, standard input, logs or ordinary files (D-52, D-85). The bootstrap secret lives only on a memory-backed file (D-68).
- No commit, push or merge unless the owner asks for it in that request. The commit steps below are written for when the owner has asked.
- Every decision here is a requirement or a direction. Apart from the Phase 1 scaffold below, M1 and M2, nothing in this plan is implemented, and no security control counts as verified until a test demonstrates it (`security.md` 18).
- Tests that need `internal/` access live inside the Go module (D-27). Security regression tests are required for every security-critical task (`security.md` 16).

## Review Focus

These inputs are implied by the spec and are exercised by named tests in the tasks that own them.

1. Legacy and numeric host spellings (`127.1`, `2130706433`, `0x7f.0.0.1`, `0177.0.0.1`, fullwidth digits) must be ambiguous and denied. Owner: Task 1.2.
2. A name with trailing dots, upper case, a leading wildcard, an underscore or a non-ASCII byte must not reach a comparison in non-canonical form. Owner: Task 1.2.
3. An exclusion must beat a matching inclusion for every rule kind, port and IP form, and adding an exclusion must never turn a denial into an allow. Owner: Task 1.4 and 1.5.
4. Port edge cases (`0`, `65536`, `08080`, duplicates, no port) and a redirect to another port. Owner: Task 1.3 and 1.4.
5. Hostile approval and job races: two workers claiming one job, a retry claim, a revocation racing a claim. Owner: M2 and M3.

## Acceptance criteria for the MVP

The MVP is accepted when, on the baseline host, a researcher can register a program and a local lab target, validate authorization with an attestation, run passive reconnaissance with an enabled source, probe an in-scope lab host, collect and verify evidence, review a candidate finding, verify it as a human, and export a Markdown report, while every denial and approval is audited, and the gates above pass. No external target is involved.

**M2 rulings (made while writing and reviewing the M2 task list):**
- The decision function takes no `actor`, because the order table of `structure.md` 5.6 does not let `scope` import `actor`. AI exclusion happens in `approval` (a non-human actor cannot request, approve, reject or revoke) and in the application use cases (P-02).
- `Category` is the closed input of an `Operation`. A class is derived (D-59) and never supplied, so a class in an AI proposal has no effect (FR-APPROVAL-004 AC5). A state-changing `http_method` raises the class to Intrusive on any category and `CONNECT` is refused. Whether a category matches the tool and the manifest is the M10 check.
- `Limits` holds the three values an approval binds (D-55): concurrency, total duration and request rate. Timeout and output size belong to the sandbox and the tool manifest (M8, M10). No numeric default is set anywhere, because the numbers come from the D-71 gate. An active operation whose limits are zero is blocked.
- Concurrency means the number of jobs that run at the same time under one approval. The per-job share of the request rate is the rate divided by that number, so the sum never exceeds the approved rate.
- `AuthorizationTTL` of 5 seconds is the lifetime of an `AuthorizedOperation`. It is a value chosen here, short against the 30 second stop objective, and the owner may change it. `Verify` cannot see a revocation. The executor calls it immediately before the process starts and records the launch through `AuthorizeLaunch` in the same step.
- An `AuthorizedOperation` is for one job (a job id is mandatory at E2 and E3).
- Terms take any future expiry and any positive number of uses. Lifetime and use ceilings are policy values owned by the policy store (M16), and the approval use case of M19 must check the terms against them before it calls `Approve`. The schema has no ceiling either.
- A pending approval at E1 gives `require_approval`. At E2 and E3 it denies.
- Every transition and every refused state change returns the zero `Approval` and an error. The caller keeps the value it had.
- An intrusive job that holds a use and never launched cannot be claimed again (D-49). It fails closed and the researcher approves again.
- A passive operation declares the port that scope is evaluated on, as the scope engine needs one.
- Attempts are recorded on the `Use` inside the `Approval` value, and the launch time is the start time of the latest attempt. The persistence mapping (M3) stores them on `jobs` and `job_attempts` (`started_at`), as the data dictionary says.
- E4 (promoting a discovered asset) is not built. It needs the asset domain (M20, TD-M2-11).

**M4 rulings (made while building, for the owner to confirm)**
- Password policy: 12 to 128 characters, valid UTF-8, no control characters, not equal to the username, no composition rules, no normalization. Usernames are lower-case ASCII `[a-z0-9._-]`, 3 to 64 characters. Login accepts any case and lower-cases the input.
- All of AUTH-01 to AUTH-10 are in M4, including the session list and the password change.
- The session CSRF token is `HMAC-SHA256(session token, "morningstar csrf v1")`. Only its SHA-256 is stored, so `GET /session` can return it again without a stored secret. The pre-session token (`ms_anon`) is signed with a per-process key and lasts 15 minutes, so a restart invalidates it.
- Cookies: `HttpOnly`, `SameSite=Strict`, `Path=/`, no `Domain`. `Secure` only when the request used TLS. Names are `ms_session` and `ms_anon`, with no `__Host-` prefix because it needs `Secure`.
- Origin is required on every non-GET request, with an exact allow-list (`MORNINGSTAR_HTTP_ALLOWED_ORIGINS`, default `http://127.0.0.1:3000,http://localhost:3000`, an assumption). `null`, a missing Origin and `Sec-Fetch-Site: cross-site` are refused. Order of checks: Host, recovery gate, JSON body, client rate limit, session, session rate limit, Origin, CSRF.
- The client key of the rate limit is the constant `loopback` for every local caller. Nothing the caller controls can pick another bucket. The cost is that one local caller can use the budget of all (the accepted limitation below).
- The attempt limit counts effective failures (failed rows minus success rows) in 15 minutes, under an advisory lock, and records the attempt before any hashing starts. Password guesses (login, re-authentication, reconcile) share one budget. Recovery-code guesses and bootstrap guesses each have their own.
- `GET /session` has its own limit of 300 per minute per client instead of RL-AUTH (the design text was changed, AUTH-01). The owner accepted it for the MVP on 2026-11-18, with the local starvation risk written down.
- The reconcile response carries the new `recoveryCode`. The design did not return it, and without it the user would have no code after a reconciliation (`RecoveryReconcileResult` in `openapi.yaml` and AUTH-10 were changed). The owner approved this on 2026-11-18.
- The reconcile request carries `newPassword` (owner decision of 2026-11-18). It must differ from the restored password, which is my reading of "set a new password": an equal value would keep a restored hash that may be older than a rotation.
- The re-authentication grant lasts 120 seconds, is single use and is bound to the session, the purpose and the SHA-256 of a canonical subject. `Reauth.Consume` runs in the caller's transaction and is the contract for M16 to M19.

**The semantics**
- `Require`: the record that an operation needs before it may start. Inside the transaction of the operation it joins it, so a failed write rolls the operation back. There is no retry inside a transaction, because the failure aborts it, and no alert, because the operation did not happen. Outside a transaction it retries within the bound.
- `Record`: for an event whose operation already took effect or was denied (a denial, a revocation, a cancellation). It always commits on its own and never changes the outcome. Only a failure to reach the database is retried. A refused privilege or constraint is not, but it still raises the alert. Each attempt has its own timeout and does not depend on the request context, so a client that left does not cancel the record of its denial.
- Exhaustion raises one open alert (`system_alerts`, kind `audit_retry_exhausted`, at most one by a unique index). The alert names the lost event by action, outcome, request id, attempts and a cause class. It never carries the event detail or the text of an error. If the alert cannot be stored, it is kept in memory and `Gate` denies until it is stored.
- `Gate` denies while an alert is open, while a raised alert is waiting to be stored and whenever the state cannot be read.

**M5 rulings (made while building, for the owner to confirm)**
- The retry numbers above are provisional.
- `Require` and `Record` are two methods and not one with a flag, so a caller chooses the semantics by what the event records. A revocation is recorded after its commit, and a crash between the commit and the record loses that record without an alert, because there is no outbox (class D).
- Only an unreachable database is retried.
- A rate-limited refusal is recorded once per action and per attempt window (15 minutes), and the next record after the window reports how many refusals the window suppressed. A refusal for a wrong credential is never coalesced. The window is the lockout window of M4, not a number of the design.
- The request id is always generated by the server. API-13 changed from "accepted when it is a UUID" to "ignored".
- The action catalog is the document `domain-model.md` section 5, extended by `system.first_run`, which the recovery code of M3 already wrote. A test keeps the code and the document equal.
- The detail is redacted by key name (a value under a secret key becomes `[redacted]` and the event is still written) and by a few value shapes. A detail that a caller builds wrongly (a bad key, too deep, too large) is refused, and the caller decides what to do.
- `Gate` is not called by any route in M5. The M4 routes must keep working while audit is down (revocation, denial), and the operations that start work do not exist yet (TD-M5-01).
- `Event` has no timestamp: the time of an event is the database clock (`occurred_at`, DB-08).
- Rows written before migration 00016 keep the actor kind `system` with the reference `anonymous` in development databases, because audit rows are append-only.
